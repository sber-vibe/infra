# Backend: административная панель и доступ (ADM-01…ADM-08)

Frontend уже работает по этим правилам. Правки по участникам описаны в «Административная панель и регистрация специалиста».
Полный контракт: `Frontend/docs/API_CONTRACT.md`. Пока сервер чего-то не поддерживает, frontend показывает
«… пока недоступна» и ничего не выдаёт за сохранённое.

## Что не заработает без backend

| Возможность frontend | Что нужно от backend | Без этого |
|---|---|---|
| Программы и перечни | `GET/POST /admin/programs`, `PUT /admin/programs/{code}` | «Настройка программ субсидий пока недоступна» |
| Перечни только из распознаваемых видов | `GET /document-types` | перечни не редактируются |
| Условные документы по признаку | `GET /application-attributes`, `conditionAttribute` в программе | условие сохраняется только текстом, автоматически не проверяется |
| Признак проекта в заявке | `attributes` в заявке, `PATCH /applications/{id}` | панели «Признаки проекта» нет |
| Правила с параметрами | `GET /admin/rules`, `PUT /admin/rules/{code}` | «Настройка правил проверки пока недоступна» |
| Общий журнал | `GET /admin/journal` с `limit`, `before`, `action` | «Общий журнал действий пока недоступен» |

## ADM-02, ADM-07. Права проверяет сервер, отказ по умолчанию

- `/api/v1/admin/**` доступен только роли `admin`. Это правило проверяется раньше общего правила для `/api/**`.
- Заявки, документы, оригиналы, проверка и решение доступны только роли `specialist`. Роль `admin` сама по себе этого права не даёт.
- Нет действующего токена → `401`. Токен есть, но не хватает роли → `403`. Оба ответа в формате Problem Details.
  На `403` frontend пишет «Недостаточно прав» и сессию не завершает.
- Если OIDC/JWT не настроен, сервер не отвечает данными без проверки. Открытый режим допустим только в явном
  профиле разработки, а не по умолчанию.
- Frontend больше не подставляет роль `specialist` по умолчанию. Пользователь без ролей видит
  «Нет доступа к рабочему месту». Роли для сервера берутся только из токена, а не из тела запроса.
- Демо-вход с выбором роли в сдаваемой сборке выключен. Если он включён для разработки, его роль не должна давать прав на сервере.

## ADM-08, ADM-01. Программы и перечни

**`GET /document-types`** → справочник видов документов, которые сервер умеет распознавать. Frontend предлагает
в перечне программы только эти виды, произвольный код ввести нельзя. Виды, которых нет в справочнике, показываются
с пометкой «нет в справочнике сервера», их можно только убрать.

**`GET /admin/programs`** → все программы, включая отключённые. **`POST /admin/programs`**, **`PUT /admin/programs/{code}`**:

```json
{ "code": "INNOVATION", "name": "Инновационный проект", "description": "…", "active": true,
  "documents": [
    { "type": "APPLICATION", "requirement": "REQUIRED" },
    { "type": "CONFORMITY_CERTIFICATE", "requirement": "CONDITIONAL",
      "condition": "если продукция подлежит сертификации", "conditionAttribute": "requiresCertification" } ],
  "version": 3, "updatedBy": "Иван Админ", "updatedAt": "2026-10-10T09:00:00Z" }
```

Сервер проверяет:
- код уникален, название не пустое;
- в перечне есть хотя бы один обязательный документ, один вид указан не больше одного раза, все виды из справочника;
- у условного документа есть `conditionAttribute` из списка признаков и непустое `condition`.

Ошибки возвращаются как `400`/`422` Problem Details с понятным `detail`. Если есть `errors[]` с `field`, frontend может показать их у полей.

- `version` защищает от одновременной перезаписи. Если PUT пришёл с устаревшей версией, сервер отвечает `409`, и frontend
  пишет «Настройку уже изменил другой администратор».
- `updatedBy` и `updatedAt` сервер берёт из токена и своих часов. Значения клиента он не принимает.
- Использованную программу лучше отключать (`active: false`), а не удалять.
- Настройки хранятся в БД и сохраняются после перезапуска. Начальные три перечня берутся из кейса.

## ADM-03. Условные документы по признаку проекта

**`GET /application-attributes`** → признаки, от которых зависят условные документы:

```json
[ { "code": "requiresCertification", "name": "Продукция подлежит сертификации" },
  { "code": "usesWaterArea", "name": "Используется акватория" } ]
```

Заявка (`ApplicationView`) получает поле `attributes`, например `{ "requiresCertification": true, "usesWaterArea": null }`.
Значение `null` или отсутствующий ключ означают «неизвестно».

**`PATCH /applications/{id}`** `{ "attributes": { "requiresCertification": true } }` → заявка. Признак указывает специалист.
- Сервер сбрасывает отчёт (`report: null`) и записывает в журнал, кто и когда указал признак и какое значение было до этого.
- Если признак может извлечь модель, это допустимо, но специалист должен видеть его и иметь возможность исправить.

Комплектность (`report.completeness[]`) для условного документа:

| Признак | Документ есть | Статус |
|---|---|---|
| `true` | нет | `CONDITIONAL_MISSING` — замечание |
| `true` | да | `FOUND` |
| `false` | нет | строка не выводится, замечания нет |
| `null` / нет | нет | `CONDITIONAL_UNKNOWN` — применимость не определена, это не «не требуется» |

В строке передаются `conditionAttribute` и `condition`. Отсутствие обязательного документа — ошибка, условного — замечание.
Лишний документ получает статус `EXTRA` и остаётся в пакете.

## ADM-04, ADM-05. Правила с параметрами

**`GET /admin/rules`**, **`PUT /admin/rules/{code}`**:

```json
{ "code": "OWN_FUNDS_SHARE", "name": "Доля собственных средств", "enabled": true, "severity": "ERROR",
  "documentTypes": ["COST_JUSTIFICATION"], "params": { "minOwnFundsShare": 0.5 },
  "paramSchema": { "minOwnFundsShare": { "kind": "percent", "label": "Минимальная доля собственных средств",
                                          "unit": "%", "min": 0, "max": 100 } },
  "version": 3, "updatedBy": "Иван Админ", "updatedAt": "2026-10-10T09:00:00Z" }
```

- `paramSchema` описывает каждый параметр:
  - `kind`: `percent`, `number`, `integer`, `money`, `text`, `boolean` или `list`;
  - `label`, `unit`, `hint`;
  - `min` и `max` в единицах интерфейса;
  - `required`, по умолчанию `true`.

  Без `paramSchema` frontend берёт встроенные описания известных ключей, но схема с сервера надёжнее.
- `percent`: администратор вводит 50, в API приходит доля `0.5`. Сервер хранит и применяет долю.
- Сервер повторяет все проверки: пустое значение, не число, значение вне границ, дробное там, где нужно целое.
  При ошибке ответ `400`/`422`, и прежняя версия правила продолжает действовать. Пустое значение никогда не превращается в 0.
- Параметр «допустимое расхождение» нельзя молча включить вместо требуемого равенства. По умолчанию он равен 0.
- Сохранение создаёт новую версию настроек. Новая проверка, в том числе повторная проверка существующей заявки,
  берёт актуальную версию в момент запуска. Фоновая проверка, которая уже идёт, заканчивается на своей версии.
  Завершённые отчёты не пересчитываются. Отчёт может содержать версию настроек, по которой он построен.
- Сценарий для проверки: пакет с долей 55% проходит порог 50%. Администратор ставит 60%, новая проверка того же пакета даёт ошибку.
- Устаревшая `version` → `409`.

## ADM-06. Журнал

**`GET /admin/journal?limit=50[&before=<ISO>][&action=<код>]`** → `JournalEntry[]`, новые записи сверху.
- `before` возвращает записи строго раньше указанного момента. Так frontend подгружает «Показать более ранние»,
  пока сервер возвращает полные страницы.
- `action` фильтрует по коду действия: `PROGRAM_CHANGED`, `RULE_CHANGED`, `CHECK_COMPLETED`, `DECISION_MADE`,
  `DOCUMENT_TYPE_CHANGED`, `FIELD_CHANGED`, `PROCESSING_FAILED`, `ACCESS_DENIED`.
- При изменении настроек в записи передаются:
  - `before` и `after`: прежнее и новое значение, объект или скаляр;
  - `version`: версия настроек после изменения;
  - `objectType`: `PROGRAM`, `RULE`, `APPLICATION` или `USER`;
  - `objectId`.

  Frontend показывает только поля, которые изменились.
- При отказе передаются `outcome: "FAILED"` и `reason`.
- Записи формирует только сервер: автора и время клиент не присылает. Изменять и очищать журнал через API нельзя.
- Если запись в журнал не удалась, изменение настройки не должно считаться успешным, то есть ответ не `200`.

## Как проверить

- Специалист отправляет `PUT /admin/rules/OWN_FUNDS_SHARE` → `403`. Администратор сохраняет → `200`, в журнале есть `before`/`after`.
- Запрос без токена к `/admin/**` и к оригиналу файла → `401`.
- `PUT` правила с `minOwnFundsShare: null`, `-0.1` или `1.01` → `400`/`422`, правило не изменилось.
- Два PUT с одной и той же `version`: второй получает `409`.
- Условный сертификат при признаке `true`/`false`/`null` → `CONDITIONAL_MISSING`, нет строки, `CONDITIONAL_UNKNOWN`.
- После перезапуска программы, правила, версии и журнал сохранились.
